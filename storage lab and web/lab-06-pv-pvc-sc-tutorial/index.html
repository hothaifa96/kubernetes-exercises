Core Concepts

Why Storage Matters in Kubernetes?

Containers are ephemeral — when a pod dies, all data in its filesystem is lost. For stateful applications (databases, logs, file uploads), you need persistent storage that survives pod restarts and rescheduling.

Key Insight: Kubernetes decouples storage from compute. A pod can be rescheduled to any node, but its data remains accessible via a PersistentVolume.

Static vs Dynamic Provisioning

Static Provisioning: Admin manually creates PVs. PVCs bind to existing PVs. Good for predictable, pre-allocated storage.

Dynamic Provisioning: When a PVC is created, the StorageClass automatically provisions a new PV. This is the modern, recommended approach for cloud environments.

Minikube Note: Minikube includes a default StorageClass called standard that uses the host's filesystem. This makes dynamic provisioning work out of the box.

StorageClass

What is a StorageClass?

A StorageClass defines different "classes" of storage. It specifies which provisioner to use (e.g., AWS EBS, GCE PD, Azure Disk, local storage) and any parameters for that storage type.

Think of it as a storage profile — "fast SSD", "standard HDD", "NFS share", etc.

Key Fields

  • provisioner: The driver that creates the actual storage (e.g., kubernetes.io/aws-ebs)
  • parameters: Provider-specific settings (e.g., IOPS, type, replication)
  • reclaimPolicy: What happens when PVC is deleted (Delete or Retain)
  • volumeBindingMode: When binding happens (Immediate or WaitForFirstConsumer)

Example: StorageClass for Fast SSD

# storageclass-fast-ssd.yaml apiVersion: storage.k8s.io/v1 kind: StorageClass metadata: name: fast-ssd provisioner: kubernetes.io/aws-ebs parameters: type: gp3 iops: "3000" encrypted: "true" reclaimPolicy: Delete volumeBindingMode: WaitForFirstConsumer

Pro Tip: Always check the default StorageClass in your cluster with kubectl get storageclass. If one is marked as default, PVCs without a specified StorageClass will use it automatically.

PersistentVolume (PV)

What is a PersistentVolume?

A PV is a cluster-level resource that represents a piece of storage in the cluster. It is independent of the lifecycle of any pod using it.

PVs can be provisioned statically (by an admin) or dynamically (by a StorageClass when a PVC is created).

Key Fields

  • capacity: Storage size (e.g., 10Gi)
  • accessModes: How the volume can be accessed (RWO, RWX, ROX)
  • persistentVolumeReclaimPolicy: What happens after PVC deletion
  • storageClassName: Which StorageClass to use (optional)
  • hostPath / nfs / awsElasticBlockStore: The actual storage backend

Access Modes Explained

Mode Full Name Description
RWO ReadWriteOnce Can be mounted by a single node (read-write)
RWX ReadWriteMany Can be mounted by multiple nodes (read-write)
ROX ReadOnlyMany Can be mounted by multiple nodes (read-only)

Example: Static PV (hostPath)

# pv-static.yaml apiVersion: v1 kind: PersistentVolume metadata: name: pv-static-example spec: capacity: storage: 5Gi accessModes: - ReadWriteOnce persistentVolumeReclaimPolicy: Retain hostPath: path: /mnt/data
Warning: hostPath is only suitable for development/testing. In production, use cloud provider volumes (EBS, PD, Azure Disk) or network storage (NFS, Ceph).

PersistentVolumeClaim (PVC)

What is a PersistentVolumeClaim?

A PVC is a namespace-scoped resource that requests storage from the cluster. Think of it as a "storage order" — the pod says "I need 5Gi of storage", and Kubernetes finds or creates a matching PV.

PVCs are what developers actually use. They don't care about the underlying storage — they just claim what they need.

Key Fields

  • accessModes: Required access mode (must match PV)
  • resources.requests.storage: How much storage is needed
  • storageClassName: Which StorageClass to use for dynamic provisioning

Example: PVC Requesting 5Gi

# pvc-request.yaml apiVersion: v1 kind: PersistentVolumeClaim metadata: name: my-pvc spec: accessModes: - ReadWriteOnce resources: requests: storage: 5Gi storageClassName: standard

Using a PVC in a Pod

# pod-with-pvc.yaml apiVersion: v1 kind: Pod metadata: name: my-pod spec: containers: - name: app image: nginx volumeMounts: - name: my-storage mountPath: /data volumes: - name: my-storage persistentVolumeClaim: claimName: my-pvc
Best Practice: Always specify storageClassName in your PVC unless you explicitly want to use the cluster's default. This makes your manifests portable across clusters.

Binding Rules

A PVC binds to a PV based on matching criteria:

  • Storage capacity must be ≥ requested size
  • Access modes must match (or be compatible)
  • StorageClass must match (or both be empty)
  • Labels/Selectors can be used for more control

Binding States

State Meaning
Available PV is free, not bound to any PVC
Bound PV is bound to a PVC
Released PVC deleted, PV still holds data (reclaim decides next step)
Failed Automatic reclamation failed

Reclaim Policies

What happens to the PV when the PVC is deleted?

Policy Behavior Use Case
Retain PV remains, data kept, needs manual cleanup Production, data safety
Delete PV and underlying storage are deleted Dev/test, dynamic provisioning
Recycle Deprecated — scrub data and make available Legacy only
Production Advice: Use Retain policy for critical data. With Delete, a simple kubectl delete pvc can wipe your data.
